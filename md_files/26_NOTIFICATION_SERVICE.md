# Notification Service — Centralized Hospital Communication & Alert Management

## 1. MODULE PURPOSE

Build a centralized, reusable **Notification Service** for the Hospital Administrative Automation & RPA Platform.

This module is responsible for creating, scheduling, sending, tracking, retrying, and auditing notifications generated by all hospital modules.

The Notification Service must support:

- SMS notifications
- Email notifications
- In-app notifications
- Push notifications if configured later
- Notification templates
- Immediate notifications
- Scheduled notifications
- Reminder notifications
- Escalation notifications
- Internal staff alerts
- Patient notifications
- Delivery tracking
- Failure handling
- Retry management
- Notification preferences
- Notification history
- Template versioning
- Bulk notifications where authorized
- RPA-triggered notifications
- External provider integration
- Delivery reconciliation
- Audit logging
- Sensitive-information protection

The Notification Service is a **shared platform service**, not a separate business module.

All other modules must call this service rather than implementing their own independent notification engine.

# 3. SYSTEM OF RECORD

MongoDB stores:

- Notification requests
- Notification messages
- Delivery attempts
- Provider responses
- Delivery statuses
- Template versions
- User notification preferences
- Scheduling information
- Failure information
- Audit references

External providers remain responsible for actual delivery.

The hospital platform must not falsely mark a notification as delivered simply because an API request was accepted.

# 4. NOTIFICATION LIFECYCLE

Standard lifecycle:

```text
Notification Requested
        ↓
Validated
        ↓
Queued
        ↓
Processing
        ↓
Sent to Provider
        ↓
Provider Accepted
        ↓
Delivery Confirmation
        ↓
DELIVERED
```

Failure:

```text
Processing
    ↓
Provider Error
    ↓
Retry
    ↓
Retry Limit Reached
    ↓
FAILED
```

Unknown state:

```text
Provider Request
      ↓
Timeout
      ↓
UNKNOWN
      ↓
Reconciliation
      ↓
DELIVERED / FAILED / UNKNOWN
```

Never blindly resend a notification when the previous provider request may already have succeeded.

# 14. IMPORTANT DELIVERY RULE

Provider API acceptance does not necessarily mean delivery.

Example:

```text
Hospital System
     ↓
SMS Provider
     ↓
HTTP 200
```

This should normally mean:

```text
PROVIDER_ACCEPTED
```

not automatically:

```text
DELIVERED
```

Delivery should be updated using:

- provider callback/webhook
- provider delivery-status API
- reconciliation job

where supported.

---

# 15. EMAIL DELIVERY

Email provider may return:

```text
accepted
```

but the recipient may later:

- receive it
- bounce it
- reject it
- mark it invalid

The system must distinguish:

```text
ACCEPTED
DELIVERED
BOUNCED
FAILED
```

internally normalize them appropriately.

Never overwrite an already-used template version.


# 33. QUEUE ARCHITECTURE

Notifications should be processed asynchronously.

Recommended:

```text
Hospital Module
      ↓
Notification API
      ↓
MongoDB
      ↓
Notification Queue
      ↓
Notification Worker
      ↓

```

The implementation may use a queue technology appropriate to the project.

The exact queue implementation should be abstracted so it can be replaced later.

---

# 34. SYNCHRONOUS VS ASYNCHRONOUS

Do not make business workflows wait unnecessarily for external notification delivery.

Example:

```text
Appointment created
       ↓
Appointment saved
       ↓
Notification queued
       ↓
API returns success
```

The appointment should not fail merely because the SMS provider is temporarily unavailable.

---

# 35. NOTIFICATION FAILURE MUST NOT CANCEL BUSINESS TRANSACTION

Example:

```text
Appointment booking
        ↓
Appointment successfully created
        ↓
SMS provider unavailable
```

Result:

```text
Appointment = CONFIRMED
Notification = FAILED
```

Do not cancel the appointment.

The system should retry the notification according to policy.

---

# 36. RETRY POLICY

Retry only retryable failures.

Retryable:

```text
TIMEOUT
TEMPORARY_PROVIDER_ERROR
RATE_LIMIT
NETWORK_ERROR
```

Usually non-retryable:

```text
INVALID_PHONE
INVALID_EMAIL
INVALID_TEMPLATE
UNAUTHORIZED_PROVIDER_REQUEST
UNSUBSCRIBED
PERMANENT_PROVIDER_ERROR
```

---

# 37. RETRY BACKOFF

Use configurable exponential/backoff behavior.

Example:

```text
Attempt 1
↓
1 minute
↓
Attempt 2
↓
5 minutes
↓
Attempt 3
↓
15 minutes
```

These are example values.

Make them configurable.

---

# 38. MAXIMUM RETRIES

Example:

```text
maxAttempts = 3
```

After the limit:

```text
FAILED
```

and create an appropriate operational exception if required.

Do not retry forever.

---

# 39. UNKNOWN PROVIDER STATE

If:

```text
request sent
      ↓
timeout
```

the result may be unknown.

Do not automatically send another notification.

Instead:

```text
UNKNOWN
   ↓
Reconciliation
   ↓
Provider status check
   ↓
DELIVERED / FAILED / UNKNOWN
```

This prevents duplicate SMS/email messages.

---

# 41. WEBHOOK SECURITY

Implement:

- Signature validation
- Timestamp validation where supported
- Replay protection
- Idempotency
- Rate limiting
- Payload validation

Never trust webhook data blindly.

---

# 42. WEBHOOK IDEMPOTENCY

The same provider callback may arrive more than once.

The system must handle:

```text
Webhook #1
Webhook #2
Webhook #3
```

without creating duplicate records or corrupting status.
